## 방식
- 폴더 `deriv/signal_a/w1` … `w8`(각각 SPEC.md·run.py·report.md·out/), 워크플로 `signal-a-stage2.yml`(deriv-research 가지, `deriv/signal_a/run2.txt` push 로 시작, 줄기를 매트릭스로 동시에, 조각 60분 이내, 3번까지 다시, 저장은 pull --rebase --autostash). 1차 파이프라인 코드(sa_common·sa_judge·sa_s3·sa_pipeline)를 불러 쓰되 고치지 않는다 — 꼭 고쳐야 하면 새 파일로 복사해 쓴다.
- **1차·X1 결과는 덮어쓰지 않는다**: t1~t6, s3, x1, REPORT.md, signals/final_v1.json, state/status.json 의 stage. 2차 상태는 `state/stage2.json`.
- 줄기마다 돌리기 전에 SPEC.md 에 시험 목록·가짓수를 적고 그대로 돌린다. 결과를 본 뒤 고치지 않는다. 가짓수는 state/ledger.json 에 더한다(2차를 더하면 가짓수 보정이 그만큼 엄해진다는 것을 보고서에 적는다).
- **보고서는 GitHub 가 끝까지 쓴다**: 모든 줄기가 끝나면 워크플로가 `deriv/signal_a/REPORT2.md` 를 만든다 — 결론 먼저(규칙으로 자동 작성), 줄기별 표(통과·관찰·다음 해 기준·네 거름·최종 후보 수, 가장 좋은 절차), 1차 관찰 목록 3개와 견준 표(더 나은 것이 나왔는지, 같은 뿌리인지), W8 참고 분석 표, 여전히 못 푼 것(W9), 끝에 "투자 권유 아님". 전체 기간 숫자와 다음 해 성적을 칸을 나눠 따로 적는다.
- **2차에서 새로 생긴 아쉬운 줄기도 보고한다(사용자 지시 2026-11-24)**: 1차와 같은 다섯 경우(관찰은 있는데 통과 없음 / 다음 해 성적은 넘었는데 거래 수 모자람 / 2026년을 넣고 빼면 결론이 바뀜 / 조각이 끝내 실패해 못 본 부분 / SPEC '안 넣은 것' 칸)를 GitHub 가 줄기마다 자동으로 가려 `state/stage2.json` 의 wish 목록, REPORT2.md 의 '아쉬운 줄기' 절, 끝 카카오톡(개수와 가장 가까웠던 것 1개)에 적는다. 자동으로 다시 돌리지 않는다 — 돌릴지는 사용자가 정한다.
- 관찰 목록은 바꾸지 않는다. 네 거름(REPORT 4절)을 모두 넘고 1차 관찰 목록과 뿌리가 다른 것이 나오면 `signals/final_v2_proposal.json` 에 **제안으로만** 적는다(넣을지는 사용자가 정한다). 최종 후보(CRITERIA 전부)가 나오면 보고서 맨 위에 적는다.
- 카카오톡: 전부 끝났을 때 1통([Signal A 2차], 200자 이내, 결론·핵심 숫자), 같은 오류로 3번 실패한 줄기가 있으면 그때 1통. 틀린 숫자가 나가지 않게, 줄기 결과가 비정상(대상 0개·읽기 실패)이면 보내지 말고 실패로 처리한다.
- 자료를 읽지 못하면 조용히 넘기지 말고 멈춘다(X1 1차의 실수). 연구소 candidates.pkl 은 판다스 최신판으로 저장돼 고정판(2.3.3)으로 읽히지 않는다 — x1/extract.py 방식(연구소와 같은 환경에서 날짜 글자로 옮김)을 쓴다.
